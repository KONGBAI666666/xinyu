七个关键问题

1. Java 为什么不能/不应该继续直接承担 AI 核心逻辑

生态不匹配: LLM SDK (openai-python)、向量数据库 SDK (qdrant-client)、文档解析 (PyMuPDF) 都是 Python 原生库。Java 对应库 (LangChain4j, Qdrant Java gRPC) 生态明显滞后, 文档少, 更新慢。

Prompt 工程是动态的: Prompt 模板、记忆提取策略、RAG 分块策略需要频繁调整。Python 修改即生效 (uvicorn --reload), Java 改模板要重新编译打包。

AI 链路天然是 Python 世界: 未来 Agent / Tool Calling / RAG 高级技巧, 90% 的教程和开源项目都是 Python。Java 做这些会变成"翻译工作"而非"能力建设"。

关注点分离: Java 专注业务 (鉴权/持久化/统计), Python 专注 AI (LLM/向量化/记忆), 各自演进不互相拖累。

2. Python AI Service 为什么独立出来

独立部署: Python 服务可单独扩容 (GPU 节点), 不影响 Java 业务服务。Docker 容器隔离, 资源配置独立。

独立迭代: Prompt 调优、模型切换、分块策略调整只需要重启 Python 容器, 不碰 Java/MySQL。

技术栈自由: Python 可以自由使用 openai, qdrant-client, PyMuPDF, aiohttp 等库, 不需要在 pom.xml 里找 Java 替代品。

学习价值: 你同时掌握了 Java 后端和 Python AI 应用开发, 这是目前最主流的"全栈 AI 应用"模式。

3. Java 和 Python 之间通过什么协议通信

协议: HTTP REST (JSON body)

基础 URL: 由 AiServiceProperties 配置, dev 为 http://localhost:9100, Docker 为 http://ai-service:9100

HTTP 客户端: Java 侧使用原生 HttpURLConnection (不用 WebClient/RestTemplate), 避免引入额外依赖, 代码更直观易读。

内容格式: 请求为 JSON (Jackson 序列化), 响应分两种:

  • 普通接口: JSON (/ai/memory/extract, /ai/rag/process)
  • 聊天接口: SSE 流 (/ai/chat/stream, Content-Type: text/event-stream)

5. SSE 在整个链路中的作用

SSE (Server-Sent Events) 是 从 LLM 到用户浏览器的流式文本传输管道, 贯穿三个层:

  1. Python → LLM API: stream=True 参数, LLM 逐 chunk 返回 (非 SSE, 是 HTTP chunked)
  2. Python → Java: FastAPI StreamingResponse, Content-Type: text/event-stream, 格式为 event: xxx\ndata: {...}\n\n
  3. Java → Vue: Spring SseEmitter, 同样格式, 前端用 EventSource 或 fetch+ReadableStream 接收

为什么用 SSE 而不是 WebSocket:

  • 单向推送 (服务端→客户端), 不需要双向
  • HTTP 协议, 不需要升级握手, 兼容 nginx 代理
  • 自动重连 (浏览器 EventSource 内置)
  • 比 WebSocket 简单, 学习成本低

SSE 事件类型:

事件触发时机数据前端行为
meta聊天开始两个消息 ID渲染"AI 思考中"占位
delta每个 token{content: "..."}打字机追加文本
done生成结束token 统计 + 状态标记完成, 停止 loading
error生成失败错误码 + 消息显示重试按钮

6. 如果 Python 服务不可用, Java 当前如何处理

聊天场景 (AiServiceClient.streamChat):

  • HTTP 连接失败 → catch(Exception) → callback.onError(51001, "AI 服务连接失败: ...")
  • Python 返回非 200 → callback.onError(51001, "AI 服务返回错误: " + code)
  • 前端收到 error 事件 → 显示"生成失败" + 重试按钮
  • 消息状态: GENERATING → FAILED (数据库标记)

记忆提取场景 (AiServiceClient.extractMemory):

  • 失败 → log.warn("记忆提取失败 (静默)") → 返回 List.of()
  • 不影响主链路, 只是本轮没有提取记忆

文档上传场景 (AiServiceClient.processDocument):

  • 失败 → 返回 {chunkCount:0, status:"ERROR", errorMsg:...}
  • 文档标记为 ERROR 状态, 提示用户重新上传

删除向量场景 (AiServiceClient.deleteRagVectors):

  • 失败 → log.warn("删除向量数据失败 (静默)")
  • MySQL 元数据已删, Qdrant 残留向量 (不影响功能, 可手动清理)
问题: 当前没有熔断机制 (如 Resilience4j)。如果 Python 持续不可用, 每个聊天请求都会等待 HTTP 超时 (10s 连接 + 180s 读超时) 才返回错误。建议: 连接超时已设 10s, 对于学习项目可接受; 如果想优化, 可加一个快速失败检查 (先 GET /health, 3s 内不通就直接报错)。

7. 哪些地方存在耦合问题

耦合点 1: 模型配置内联传递 (轻微)

  • Java 把解密后的 apiKey 明文放在 JSON body 里传给 Python
  • Python 不存储 API Key, 用完即弃, 这是正确做法
  • 但如果 Java 的 AES 密钥泄露, Key 在 HTTP 传输中可被截获
  • 当前可接受: Docker 内网通信, 不经过公网

耦合点 2: 文件内容 Base64 传输 (性能)

  • AiServiceClient.processDocument 把文件 byte[] Base64 编码后放 JSON body
  • 大文件 (10MB+) 会导致 JSON 体过大, 内存压力
  • 学习项目可接受; 如果要优化, 可改用 multipart/form-data 或先存到共享卷

耦合点 3: SSE 事件格式双端硬编码 (维护)

  • Java handleSseEvent 里硬编码了 "meta"/"delta"/"done"/"error" 字符串
  • Python routers/chat.py 也硬编码了同样的事件名
  • 如果一端改了事件名, 另一端不会编译报错, 只在运行时静默失败
  • 学习项目可接受; 生产项目可以用枚举 + 共享常量

耦合点 4: conversationId/userId 传空串 (设计妥协)

  • Java 调用 streamChat 时 conversationId, userId, characterId 都传空串
  • 因为 Python 不操作 MySQL, 这些 ID 在 Python 侧无实际用途
  • Python 只用 messages, modelConfig, ragKbId, memoryBlock
  • 不算问题: Python 作为无状态 AI 工具, 不需要知道业务上下文

三、Python AI Service 模块分析

模块 1: API 路由 (routers)

做什么: 接收 Java 的 HTTP 请求, 调用 service 层, 返回 SSE 流或 JSON

为什么 Python 负责: FastAPI 原生支持 async + StreamingResponse, 天然适合 SSE 流式输出; Python 的装饰器路由 (@router.post) 比 Java 的注解更简洁

核心技术: FastAPI, StreamingResponse, Pydantic

核心类/函数:

  • chat.py → chat_stream(req: ChatRequest) → event_generator()
  • memory.py → extract_memory(req: MemoryExtractRequest)
  • rag.py → process_document(req), search(req), delete_vectors(kbId, docId)

输入: Pydantic 模型 (ChatRequest, MemoryExtractRequest, RagProcessRequest)

输出: StreamingResponse (SSE) 或 dict (JSON)

与其他模块关系: 调用 LLM, RAG, Memory, Prompt 所有 service

模块 2: LLM (llm_client.py)

做什么: 封装 OpenAI 兼容 API 的调用, 支持流式 (SSE) 和同步两种模式

为什么 Python 负责: openai 官方 Python SDK 是一等公民, Java SDK (如 LangChain4j) 是第三方维护, 版本滞后

核心技术: openai Python SDK, AsyncOpenAI 异步客户端

核心类/函数:

  • LlmClient 类
  • stream_chat(messages, temperature, max_tokens) → AsyncIterator[tuple[str, dict]]
  • yield ("delta", {content}) / yield ("done", {promptTokens, completionTokens})
  • chat(messages, temperature, max_tokens) → 同步调用 (记忆提取用)

输入: ModelConfig (modelCode, baseUrl, apiKey) + List[ChatMessage]

输出: 异步迭代器 (流式) 或 ChatResponse (同步)

与其他模块关系: 被 chat.py (流式聊天), memory_extractor.py (记忆提取), embedding_service.py (间接, 用同一个 OpenAI client) 调用

模块 3: Prompt 编排 (prompt_assembler.py)

做什么: 把 system prompt + memory 块 + RAG 块 + 历史消息组装成发给 LLM 的完整消息序列

为什么 Python 负责: Prompt 工程需要频繁实验和调整, Python 修改即生效 (热重载)

核心技术: 纯 Python, 无依赖

核心类/函数:

  • PromptAssembler 类
  • assemble(system_prompt, history, memory_block, rag_block) → List[ChatMessage]
  • 结构: [system: prompt + memory + RAG] + [user/assistant: history]
  • MAX_CONTEXT_MESSAGES = 20 截断最近 20 条

输入: 各部分的字符串/列表

输出: List[ChatMessage] (role + content)

与其他模块关系: 被 chat.py 调用, 输入来自 Java (memory_block) 和 Python (rag_block)

模块 4: RAG (rag_service.py + embedding_service.py + document_parser.py + chunk_splitter.py)

做什么: 文档上传时解析→分块→向量化→存 Qdrant; 聊天时查询→注入 context

为什么 Python 负责:

  • PyMuPDF (fitz) 是 Python 原生 PDF 解析库, Java 对应 (PDFBox) 依赖重
  • Embedding API 调用用 openai SDK (与 LLM 共用 client)
  • Qdrant Python SDK (REST) 比 Java gRPC SDK 更稳定
  • 分块策略调整是 RAG 调优核心, 需要快速迭代

核心技术: PyMuPDF, openai embeddings, qdrant-client (REST)

核心类/函数:

  • RagService.process_document(kb_id, doc_id, file_name, file_bytes, model_config)
  • RagService.search(kb_id, query, model_config) → (chunks, rag_block)
  • EmbeddingService.embed(text) → 向量 (float list)
  • DocumentParser.parse(file_name, file_content) → 纯文本
  • ChunkSplitter.split(text) → 分块列表

输入: 文件 bytes / 查询字符串 + 模型配置

输出: chunk 数量 / 检索结果 + 注入文本

与其他模块关系: 调用 EmbeddingService, QdrantService, DocumentParser, ChunkSplitter; 被 chat.py 和 rag.py 调用

模块 5: Memory (memory_extractor.py)

做什么: 从对话中提取关键信息 (用户喜好/事实/偏好), 用 LLM 生成结构化记忆

为什么 Python 负责: Prompt 模板需要频繁调整, JSON 解析在 Python 中更自然 (json module / Pydantic)

核心技术: LLM + JSON parsing

核心类/函数:

  • MemoryExtractor 类
  • extract(dialog, model_config) → List[ExtractedMemory]
  • Prompt 模板内置: "从对话中提取长期记忆, 返回 JSON 数组..."
  • 容错: JSON 解析失败 → 正则提取 → 空列表兜底

输入: 对话文本 + 模型配置

输出: List[ExtractedMemory] (memoryKey, content, importance)

与其他模块关系: 调用 LlmClient; 被 routers/memory.py 调用

模块 6: Qdrant (qdrant_service.py)

做什么: 封装 Qdrant 向量数据库的 CRUD 操作

为什么 Python 负责: qdrant-client Python SDK 功能最全, 文档最好; Java SDK 使用 gRPC, 依赖重且版本兼容问题多

核心技术: qdrant-client Python SDK (REST API, port 6333)

核心类/函数:

  • QdrantService 类
  • ensure_collection() → 启动时自动创建集合 (如不存在)
  • upsert(kb_id, doc_id, chunks, vectors) → 批量写入向量
  • search(kb_id, query_vector, top_k) → 检索 Top-K
  • delete_by_kb(kb_id) / delete_by_doc(kb_id, doc_id)

输入: 向量 (float list) + payload (kb_id, doc_id, text)

输出: 检索结果列表 (text + score)

与其他模块关系: 被 RagService 调用; 启动时在 main.py lifespan 中调 ensure_collection

四、RAG 完整流程

五、Memory 完整流程

记忆提取 → 存储 → 注入

Memory 与普通聊天历史的区别

维度聊天历史 (history)长期记忆 (memory)
存储位置MySQL message 表MySQL memory 表
生成方式用户和 AI 直接产生LLM 从对话中提取
保留时长按会话隔离, 删会话即清跨会话持久, 按用户+角色
注入方式全部历史 (最近20条) 作为 messagesTop-5 拼到 system prompt
数据结构{role, content}{memoryKey, content, importance}
Token 成本每轮都消耗 (历史消息全传)仅 5 条, 成本极低
去重不去重同 memoryKey 更新

核心区别: 聊天历史是"流水账", 记忆是"摘要"。历史消息每轮全量传给 LLM (消耗 token), 记忆只取最重要的 5 条注入 system prompt。用户可以说 100 句话, 但 LLM 只需要记住 5 条核心信息。这就是 Memory 的价值: 压缩信息 + 跨会话持久。
